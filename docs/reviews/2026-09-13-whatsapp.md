## Summary
The implementation successfully integrates Meta Cloud API for template management and campaign broadcasting. The campaign wizard and UI updates are clean. However, there are critical race conditions and idempotency issues in the delivery webhook and Inngest workers. These flaws will lead to double refunds and corrupted campaign counters. There is also a major performance issue that will crash workers on large broadcasts due to memory loading.

## Blockers
### 🔴 Race condition in webhook failure handling, `src/routes/api/webhooks/whatsapp.ts`
**Problem**: The webhook reads the message status into memory (`const existing = await prisma.message.findUnique(...)`) and then checks `if (existing.status !== "failed")` before incrementing `failedMessages` and issuing refunds.
**Why it matters**: If Meta sends duplicate webhooks concurrently, both executions will read the old status. Both will increment failure counts, decrement sent counts, and issue refunds. This leads to data corruption and financial loss.
**Suggested fix**: Use conditional updates to atomically check the status. `await prisma.message.updateMany({ where: { id: existing.id, status: { not: "failed" } }, data: { status: "failed" } })`. Only proceed to increment campaign counters and refund if `count > 0`.

## Major
### 🟠 Not idempotent Inngest step for failures, `src/features/jobs/functions/send-campaign.ts`
**Problem**: Inside the `persist-result` step, if `result.success` is false, the code increments `failedMessages` and calls `refundForMessage` without checking if this failure was already processed.
**Why it matters**: If the Inngest worker crashes or times out after updating the DB but before the step completes, Inngest will retry the step. The retry will execute the increment and refund again. This leads to double counting and double refunds.
**Suggested fix**: Make the step idempotent. Update the message using `updateMany` checking that the status is still `queued` or `sending`. Only perform the increments and refunds if the `updateMany` affected exactly one row.

### 🟠 Memory exhaustion via findMany sum, `src/features/jobs/functions/send-campaign.ts`
**Problem**: In `check-complete`, the code queries all sent messages into memory just to sum their costs (`await prisma.message.findMany({ select: { costKobo: true }, where: ... })`) followed by a JS array reduce.
**Why it matters**: For a large campaign, loading all records into memory will exceed the Node heap size and crash the worker. This blocks campaign completion and hold reconciliation.
**Suggested fix**: Use the database to aggregate the sum. `await prisma.message.aggregate({ _sum: { costKobo: true }, where: { campaignId, status: "sent" } })` and use `_sum.costKobo`.

## Minor
### 🟡 Missing Sentry instrumentation for critical jobs, `src/features/jobs/functions/send-campaign.ts`
**Problem**: The orchestrator and steps are not instrumented with `Sentry.startSpan`.
**Why it matters**: Project rules mandate instrumenting critical server functions. Debugging slow dispatch at scale will be difficult without tracing.
**Suggested fix**: Wrap the main handler or expensive steps in `Sentry.startSpan` to track execution time.

## Strengths
* Good use of two phase wallet holds for expensive marketing messages.
* Atomic transition logic for the orchestrator completion step.

## Test coverage
The tests are configured and passing. However, they only mock the happy path for webhooks and workers. The test suite does not exercise concurrent webhook deliveries or Inngest retries. This misses the race condition and idempotency failures. Add tests that trigger the webhook twice simultaneously to verify the race condition is mitigated.
